RESOLVED PRODUCT AND DOMAIN DECISIONS
These decisions remove ambiguity from the historical prototype and are authoritative for Phase 1:
1. A VideoProject has zero or more SourceVideo records. SourceVideo.project is a ForeignKey, not a OneToOneField. A project can therefore hold multiple source transcripts, and all imported legacy videos can belong to one imported project.
2. A canonical YouTube video may appear once per project and may appear in different projects. Enforce UniqueConstraint(project, youtube_video_id); do not make youtube_video_id globally unique.
3. Every user-created VideoProject has a required owner ForeignKey to settings.AUTH_USER_MODEL with on_delete=PROTECT so deleting an account cannot silently destroy projects. Ordinary users may access and mutate only their own projects and sources. Staff/superusers may inspect all projects; any broader collaboration model is out of scope.
4. Legacy rows have no owner. The data migration creates or reuses one deterministic inactive system account with reserved username __legacy_transcript_import__ and an unusable password, owns one deterministic "Imported transcript history" project with it, and attaches imported SourceVideo rows to that project. Add the swappable user-model migration dependency. A preflight check must fail before canonical writes if that username is already occupied by an incompatible account. Staff must be able to inspect and explicitly reassign the imported project after migration. Never guess an owner from unrelated users.
5. Workflow stage and locking are orthogonal. VideoProject has a status chosen from draft, transcript_ready, approved, archived, and failed, plus is_locked and the timestamps approved_at, archived_at, and locked_at. Do not encode locking as a status. Do not infer any state from timestamps alone.
6. Allowed stage transitions are: draft -> transcript_ready or archived; transcript_ready -> draft, approved, failed, or archived; failed -> draft or archived; approved -> archived. Moving to transcript_ready or approved requires at least one SourceVideo and requires every attached source to have completed ingestion with at least one chunk. Archived is terminal in Phase 1. Approval is not silently reversible in Phase 1.
7. Lock is permitted only for an approved, non-archived project. Explicit unlock is permitted to the owner or staff through a POST endpoint, but unlocking does not undo approval. Archiving requires an unlocked project, so a locked project must be explicitly unlocked first. Archived projects cannot be locked or unlocked.
8. Content mutation (project content fields, adding/deleting sources, ingestion, and transcript replacement) is allowed only while the project is unapproved, unlocked, and unarchived. Workflow endpoints enforce their own transition rules. Ordinary deletion of a project or source is forbidden when the project is approved, locked, or archived. Draft/transcript-ready/failed unlocked projects may be deleted with explicit POST confirmation; project deletion intentionally cascades to its sources and chunks.
9. In Phase 2, analysis and selection require an approved but unlocked, non-archived project. Locking represents a frozen reviewed result. This rule may be changed only by an explicit product decision and corresponding tests.
10. Import provenance is durable. SourceVideo includes a nullable, unique legacy_scraped_video_id field until legacy retirement is verified. A dedicated LegacyImportConflict model/table records migration batch/version, legacy identifiers, severity (warning or error), reason code, and structured detail. Migration conflicts and normalization warnings must not exist only in logs.

TARGET ARCHITECTURE
VideoProject
  -> zero or more SourceVideo
       -> TranscriptChunk
       -> AnalysisSegment (Phase 2 only)

Canonical ownership rules:
1. VideoProject is the user-facing unit of work.
2. SourceVideo represents one YouTube source belonging to a VideoProject.
3. TranscriptChunk stores ordered transcript text and timing for one SourceVideo.
4. ScrapedVideo and TranscriptEntry are transitional legacy models, not the final domain model.
5. TranscriptService is the only application service that fetches, normalizes, deduplicates, and persists source-video transcript data.
6. HTTP views and management commands must use TranscriptService; they must not duplicate transcript-fetching or persistence logic.
7. VideoProject owns authorization and lifecycle state; SourceVideo and TranscriptChunk inherit both through their project relationship.

SCOPE
In scope:
- Restore VideoProject, SourceVideo, and TranscriptChunk as canonical models.
- Restore project create/read/update/list behavior and approval, lock, archive, and delete workflow.
- Preserve video-title retrieval, duplicate detection, and saved-transcript list/detail/delete behavior.
- Safely migrate data from ScrapedVideo and TranscriptEntry into the canonical schema.
- Restore TranscriptService and route all transcript ingestion through it.
- Add model, service, migration, view, command, workflow, and integration tests.
- Run Django migration and system validation commands.
- Define, but do not start prematurely, the AI-analysis phase.

Out of scope for the consolidation phase:
- LLM provider integration.
- Embeddings, vector databases, semantic search, or background-job infrastructure unless already present and required to keep existing behavior working.
- Video rendering, narration generation, reaction-block generation, or publishing.
- Unrelated UI redesigns or dependency upgrades.

NON-NEGOTIABLE CONSTRAINTS
1. Preserve existing user data. Never delete ScrapedVideo or TranscriptEntry tables before a verified forward data migration and a tested rollback/retention strategy exist.
2. Use additive migrations first. Separate schema creation, data migration, application cutover, and legacy-model removal into distinct migrations/commits.
3. Do not rewrite or squash migrations already applied in shared environments.
4. Do not silently merge ambiguous records. Record migration conflicts deterministically and make the migration idempotent or otherwise safe under Django migration semantics.
5. Preserve stable public URLs where practical. If URL names must change, keep redirects or compatibility aliases and test them.
6. Preserve approval/locking invariants. Approved or locked projects and their protected content must not be mutated through ordinary edit/ingestion paths.
7. Avoid business logic in views, templates, models' save methods, or management commands when it belongs in TranscriptService.
8. Make the smallest coherent changes necessary. Do not begin Phase 2 until every Phase 1 gate passes.
9. Treat every pre-existing uncommitted change as user-owned. Before editing, capture git status and the relevant diffs. Never use reset, checkout, clean, or a broad restore to obtain historical code.
10. Use a deployment-safe expand/migrate/cutover/contract sequence. A migration being reversible in a test database does not by itself make an application rollback safe after new canonical writes have begun.
11. Do not depend on the currently installed global environment. Confirm and document the dependency manifest and supported Python version before claiming reproducibility.

EXECUTION METHOD
Complete tasks in order. At every DO NOT PROCEED gate, stop immediately if a condition fails. Report the failure, relevant command output, affected files, and the smallest proposed correction. Do not bypass a gate by weakening or deleting tests.

PHASE 2 — AI TRANSCRIPT ANALYSIS (ONLY AFTER GATE APPROVAL)

PHASE 2 OBJECTIVE
Turn an approved, stable transcript into reviewable semantic segments, score those segments, and let a user select the best material without changing the source transcript.

Task 2.1: Design AnalysisSegment.
File-level targets: canonical models module plus a new additive migration.
- Add AnalysisSegment belonging to SourceVideo (and therefore indirectly to VideoProject).
- Include explicit transcript coverage: start/end chunk references or stable sequence/timing boundaries.
- Store segment order, title/summary, source text or a reproducible reference to source chunks, semantic/topic labels, score components, aggregate score, selection state, analysis version, and timestamps.
- Store provider/model/prompt or algorithm version metadata sufficient to reproduce and audit results, without storing secrets.
- Add constraints for order, boundary validity, and uniqueness per analysis version.
- Never overwrite TranscriptChunk text during analysis.

Task 2.2: Build semantic segmentation as an isolated service.
- Create an analysis service separate from TranscriptService.
- Input: a SourceVideo with ordered TranscriptChunk records.
- Output: validated segment proposals with complete source coverage rules.
- Prefer transcript timing and sentence/topic boundaries; prevent overlaps and unexplained gaps unless explicitly supported.
- Define minimum/maximum segment size and deterministic fallback segmentation for AI failure.
- Validate structured AI output before persistence.
- Make provider clients injectable and keep calls out of views/models.
- Make analysis rerunnable by version without destroying prior accepted selections.

Task 2.3: Implement scoring.
- Define transparent score dimensions before coding, such as relevance, novelty, clarity, emotional/reaction potential, factual density, and clip suitability.
- Define ranges, weights, aggregate calculation, and tie-breaking deterministically.
- Store component scores and rationale so users can understand the ranking.
- Validate and clamp/reject malformed scores rather than trusting model output.
- Tests must not call live AI services.

Task 2.4: Add selection UI.
- Add an analysis page scoped to project/source video.
- Show segment order, source timing/chunk range, text preview, summary/tags, component scores, aggregate score, rationale, and selected state.
- Allow users to select/deselect segments and preserve selections safely.
- Support filtering/sorting by score without changing canonical transcript order.
- Enforce the resolved semantics: analysis and selection require an approved, unlocked, non-archived project. Locking freezes derived analysis/selection as well as canonical content. Implement this consistently server-side.
- Use POST plus CSRF protection for mutations.

Task 2.5: Add analysis tests.
- Model constraints and ordering.
- Deterministic boundary/coverage validation.
- Structured-output validation, retry/fallback, provider failure, and transaction rollback.
- Score calculation and malformed score handling.
- Rerun/version behavior and preservation of selections.
- Selection UI authorization, state restrictions, POST enforcement, display, sorting, and persistence.
- Integration: canonical transcript -> analysis -> scored segments -> user selection.
