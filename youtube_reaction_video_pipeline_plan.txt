YOUTUBE REACTION VIDEO PIPELINE — REVISED EXECUTION PLAN
Repository: https://github.com/RimPeter/YouTubeContentCreator

PURPOSE
Build an AI-assisted Django production workstation that turns approved source transcripts into reviewable reaction-video projects and, eventually, upload-ready MP4 files. The system must preserve human editorial control, source traceability, reproducibility, and safe rollback at every stage.

This is an execution plan, not a promise to build every possible studio feature. Work proceeds through small vertical slices. A later phase may start only when the preceding gate passes.


CRITIQUE OF THE ORIGINAL BLUEPRINT

The original document contains a useful product vision, especially its emphasis on review, approval, modular reaction writing, and a vertical-slice proof of concept. It nevertheless needs the following corrections:

1. It restarts foundation, project, source, and transcript work that is already implemented. The current repository must be treated as the baseline rather than rebuilt under new apps.
2. Twenty-five mostly sequential phases delay the riskiest proof: whether one selected segment can become a coherent, rights-documented, technically valid mini-video.
3. PostgreSQL, Redis, Celery, numerous provider abstractions, voice cloning, browser automation, and publishing are prescribed before a demonstrated requirement. Add infrastructure at the phase that needs it.
4. “Screen-record every selected segment” is an unverified product decision. Clip acquisition depends on rights, platform terms, playback restrictions, ads, consent/cookie state, DRM, and technical reliability. Begin with an authorized local clip or manual upload and treat automated capture as a separately approved adapter.
5. CRUD and approve/lock behavior is repeated for every object without defining a consistent lifecycle, versioning policy, authorization model, or invalidation algorithm.
6. Downstream invalidation is described only as a warning. It requires immutable artifact versions, input fingerprints, dependency edges, idempotency keys, and deterministic stale/current state.
7. AI outputs lack provider/prompt/version metadata, schema validation, prompt-injection boundaries, cost limits, retry rules, and deterministic fallbacks.
8. Research/fact-checking needs citation provenance and human verification rules; AI-generated “evidence” cannot be treated as verified fact.
9. Media artifacts need checksums, stream metadata, storage ownership, retention, cleanup, and failure recovery before rendering work begins.
10. Voice cloning requires explicit consent, secure reference-audio handling, provider-policy review, and deletion controls. It must not be part of the first TTS milestone.
11. Fixed visual-change intervals, commentary ratios, duration targets, and LUFS values are useful hypotheses, not universal acceptance criteria. Make them configurable and validate them against actual outputs.
12. The original plan has no explicit cost budget, resource limits, cancellation semantics, observability, or protection against multiple workers producing the same artifact.


AUTHORITATIVE CURRENT BASELINE

The following work is complete and must not be rebuilt:

- VideoProject -> SourceVideo -> TranscriptChunk is the canonical persisted hierarchy.
- A project has an owner and may contain multiple source videos.
- YouTube identity is unique per project.
- TranscriptService is the single ingestion path used by HTTP views and the management command.
- Project CRUD, ownership filtering, approval, lock/unlock, archive, and protected deletion exist.
- Saved transcript list/detail/delete use canonical models.
- Legacy ScrapedVideo/TranscriptEntry data has been imported with provenance while legacy tables remain for the compatibility window.
- The local consolidation suite passes. Re-run it before beginning this plan; do not rely on the recorded result.
- Phase 2 AI analysis has not started.

Current lifecycle rules remain authoritative:

- Transcript/content mutation is allowed only before approval and while unlocked/unarchived.
- Analysis and selection require an approved, unlocked, non-archived project.
- Locking freezes canonical and derived work.
- Archived projects are terminal in the current implementation.


CORE PRODUCT PRINCIPLES

1. AI proposes; a user reviews, edits, regenerates, selects, approves, or rejects.
2. Canonical transcript chunks are never overwritten by analysis or generation.
3. Every generated artifact records the exact input versions, configuration, algorithm/prompt version, and provider/model when applicable.
4. Regeneration creates a new version. Previously approved output is retained until an explicit retention policy removes it.
5. Long-running or externally dependent work is idempotent, cancellable where practical, retry-bounded, and observable.
6. Views validate input and authorization, then call application services. Provider calls, subprocesses, persistence orchestration, and business rules do not live in views, templates, model save methods, or management commands.
7. External clients are injectable. Automated tests make no live AI, TTS, browser, stock-media, or YouTube calls.
8. Secrets never enter prompts, logs, model fields, filenames, or generated reports.
9. Untrusted transcript/web content is data, not instruction. Provider prompts delimit it and structured output is validated before persistence.
10. Source-media acquisition, voice cloning, stock assets, music, and publishing require documented rights/consent and current provider/platform-policy review before implementation or use.
11. Build one high-quality 60–120 second vertical slice before supporting a full multi-segment weekly workflow.
12. Do not retire legacy transcript tables as part of this plan. That remains a separate consolidation contract release.


CROSS-CUTTING ARTIFACT LIFECYCLE

Do not add one generic status field to every model without semantics. Use the following shared concepts consistently:

- Draft: editable generated or user-authored version.
- Running: a job currently owns generation.
- Succeeded: generation completed and validation passed.
- Failed: generation stopped with a sanitized error code/message.
- Approved: a specific version accepted by a user.
- Stale: a previously generated version whose recorded inputs no longer match current approved upstream inputs.
- Superseded: retained historical version replaced by a newer version.

Locking remains project-level. Approval is version-specific for derived artifacts. A project cannot be locked while required jobs are running or required artifacts are stale/failed.

Every derived artifact must have:

- project and owner scope inherited through relationships
- integer version or generation identifier
- status and timestamps
- created_by where user initiated
- input_fingerprint
- configuration snapshot
- provider/model/prompt/algorithm version where relevant
- sanitized error code and message where relevant
- uniqueness or idempotency constraint preventing duplicate successful output for the same generation request

Dependency invalidation must be deterministic:

UPSTREAM APPROVED VERSION CHANGES
    -> compute new input fingerprint
    -> mark only dependent current artifacts stale
    -> retain historical files and rows
    -> show exact affected artifacts
    -> require explicit regeneration/selection

Do not implement invalidation as model signals with hidden side effects. Use an application service and test the complete dependency graph.


EXECUTION METHOD

For every phase:

1. Inventory the existing tree, migrations, working-tree changes, and relevant external requirements.
2. Write the schema/service contract and acceptance tests before provider/UI breadth.
3. Use additive migrations and review generated operations.
4. Stub providers at the client boundary.
5. Run:
   - python manage.py makemigrations --check
   - python manage.py migrate
   - python manage.py check
   - python manage.py test
6. Record files, migrations, reconciliation, tests, costs/limits, remaining risks, and the next permitted phase.
7. Stop at a failed gate. Do not skip, weaken, or delete a failing test to proceed.

PHASE B — TRANSCRIPT ANALYSIS AND SEGMENT SELECTION

Objective:
Turn one approved SourceVideo transcript into auditable semantic segments, transparent scores, and an explicit ordered selection without modifying TranscriptChunk.

Models:

AnalysisRun
- source_video
- version
- status
- source_fingerprint computed from ordered chunk identity/timing/text
- provider, model, prompt_version, algorithm_version
- configuration JSON with a validated schema
- started_at, completed_at
- sanitized error_code/error_message
- created_by
- unique(source_video, version)

AnalysisSegment
- analysis_run
- order
- start_chunk and end_chunk, both belonging to the run's SourceVideo
- start_seconds and end_seconds copied for audit/display
- title, summary, source_text snapshot or reproducible chunk reference
- topic labels
- component scores
- aggregate score
- rationale
- unique(analysis_run, order)
- boundary/order/check constraints where database-portable

SegmentSelection
- project
- analysis_segment
- order
- optional reviewed start/end override constrained within the source segment
- notes
- selected_by and timestamps
- unique(project, analysis_segment) and unique(project, order)

Service design:

- AnalysisService accepts an approved, unlocked, non-archived SourceVideo.
- Provider client is injected and returns a versioned structured schema.
- Validate all chunk references, ordering, coverage, score ranges, labels, and text limits before persistence.
- Persist a complete run atomically; provider or validation failure leaves no partial segments.
- Define an explicit coverage policy. Initial policy: ordered, non-overlapping segments cover every non-empty transcript chunk exactly once.
- Provide deterministic sentence/chunk-count fallback segmentation when AI output fails validation after bounded retries.
- Reanalysis creates a new AnalysisRun and does not delete old runs or selections.
- SelectionService validates ownership, run/source/project consistency, order, boundaries, and project lifecycle.

Scoring contract:

- Define component ranges and weights in versioned configuration before coding.
- Initial candidate dimensions: relevance, clarity, factual density, novelty, controversy, reaction potential, and clip suitability.
- Store components, weights, aggregate, and rationale.
- Reject missing/non-numeric/out-of-range values; do not silently trust or clamp provider output unless the documented algorithm explicitly calls for clamping.
- Deterministic sorting: aggregate descending, then source order ascending.

UI:

- List analysis runs and show which is current/stale.
- Display source boundaries, text preview, title/summary, labels, score components, aggregate, and rationale.
- Select/deselect and order segments with POST + CSRF and ownership checks.
- Sorting/filtering must not alter canonical source order or persisted selection order accidentally.
- Show provider failure/fallback without exposing raw exceptions or prompt content.

Tests:

- Model relationships, source-boundary validation, uniqueness, ordering, and cascades/protection.
- Stable source fingerprinting.
- Valid structured response, malformed response, overlaps, gaps, wrong-source chunks, bad scores, timeout, bounded retry, deterministic fallback, and transaction rollback.
- Reanalysis/version preservation and stale-run display.
- Selection ownership, project lifecycle, ordering, POST enforcement, and cross-user denial.
- Integration: approved transcript -> analysis -> scored segments -> ordered selection.

GATE B

Do not acquire media or generate reaction scripts until analysis/selection is auditable, rerunnable, fully tested without a live provider, and all Django checks pass.


PHASE C — PRODUCTION ARTIFACT AND JOB FOUNDATION

Objective:
Create only the infrastructure required for long-running media work.

Models/services:

MediaAsset
- project
- kind
- storage key/file field; never store media blobs in normal relational fields
- checksum and byte size
- duration, width, height, frame rate where relevant
- audio/video stream presence
- MIME/container/codec metadata
- origin and rights/consent metadata
- version/status/timestamps
- owner-visible display name; storage names must not trust user filenames

PipelineJob
- project, job_type, status, progress
- idempotency_key
- requested_by
- bounded attempts
- input/configuration snapshot
- started/completed/cancelled timestamps
- sanitized error code/message
- unique active ownership for an idempotency key

ArtifactDependency
- upstream content type/id/version/fingerprint
- downstream content type/id/version
- relation type
- uniqueness preventing duplicate edges

Infrastructure decisions:

- Define local development storage and production object-storage interface.
- Validate upload size, extension, detected MIME, and media streams.
- Invoke FFmpeg/ffprobe with argument arrays, fixed executable configuration, timeouts, resource limits, and captured sanitized logs; never construct shell commands from user strings.
- Start synchronously only for a bounded proof if request time is demonstrably safe. Before capture, TTS, or rendering enters normal UI use, add a real background-job runner.
- Choose Celery/Redis only after documenting why the chosen deployment cannot meet requirements with a simpler supported queue. If selected, add health checks, retry/cancellation rules, worker concurrency limits, and transactional enqueue-on-commit behavior.
- Add cleanup/retention commands that default to dry-run and never delete approved/current assets.

GATE C

Do not start automated capture/render jobs until file validation, idempotency, dependency tracking, cancellation/failure semantics, storage isolation, and worker/tool health checks are tested.


PHASE D — ONE AUTHORIZED SOURCE CLIP

Objective:
Produce one validated clip for one selected segment.

Acquisition order:

1. First vertical slice: user supplies an authorized local source file or pre-trimmed clip.
2. Implement deterministic FFmpeg trim from a validated local source using selected timestamps and configurable padding.
3. Only after a documented rights/platform-policy review may an automated acquisition adapter be considered.
4. Browser screen recording is one optional adapter, not the domain model and not the default assumption.

Models:

SourceClip
- selected_segment
- source media asset
- requested and actual start/end
- padding configuration
- processed asset
- validation result
- version/status/approval

ClipJob
- use PipelineJob contract rather than duplicating generic job fields

Validation:

- playable file
- expected audio/video streams
- duration within configured tolerance
- timestamp bounds within source media
- supported resolution/frame rate or documented normalization
- checksum and deterministic link to the selected-segment version

Tests use tiny generated fixtures, not downloaded copyrighted material or live browser playback.

GATE D

One selected segment must reliably produce a previewable validated clip on a clean environment. Any automated acquisition approach requires separately recorded authorization and policy approval.


PHASE E — RESEARCH AND REACTION DRAFT

Objective:
Create traceable original commentary for one selected segment.

ResearchPackage / EvidenceSource:

- selected segment and version
- research question/focus
- source URL, title, publisher/author where available
- publication date and retrieval date
- supported/contradicted/uncertain classification
- concise finding and relevance
- citation metadata and archived/snapshot reference where permitted
- verification status and verified_by

Rules:

- Research output is a lead for human verification, not automatically verified fact.
- Every factual claim in generated commentary must link to transcript evidence, an EvidenceSource, or be explicitly labeled opinion/inference.
- Provider-produced URLs must be validated; never invent or silently accept inaccessible citations.
- Respect source copyright: store concise evidence notes and permitted excerpts, not copied articles.

ReactionBlock:

- selected_segment and input fingerprint
- version/status
- reframe
- focus
- reaction_type
- evaluation
- mini_essay_thesis
- mini_essay_script
- conclusion
- optional bridge
- combined_script generated reproducibly from stored subsections
- prompt/provider metadata and rationale
- approved_by/approved_at

Generate and edit subsections independently, but approve a complete ReactionBlock version for the first vertical slice. Add subsection-level approval only if real use demonstrates a need.

Tests:

- Schema validation, citation mapping, unsupported claim flags, prompt-injection fixtures, provider failure, regeneration/version retention, deterministic combined script, ownership/lifecycle, and transaction rollback.

GATE E

One approved source clip plus one approved reaction script must be coherent, traceable to evidence, and substantially original under human review. No legal conclusion is automated; obtain qualified advice where required.


PHASE F — NARRATION, VISUALS, AND MINI-VIDEO VERTICAL SLICE

Objective:
Render one 60–120 second reviewable mini-video before scaling the data model or UI.

NarrationAsset:

- ReactionBlock version/subsection
- standard VoiceProfile
- exact source text fingerprint
- provider/model/settings
- audio MediaAsset
- measured duration
- version/status/approval

Start with a standard licensed TTS voice or user-recorded narration. Voice cloning is deferred to a separate opt-in phase requiring explicit consent records, reference-audio security, deletion/export controls, and current provider-policy review.

VisualSlot / VisualAssetSelection:

- narration time range
- visual intent and search query
- asset type
- selected MediaAsset
- rights/license/source metadata
- crop/position/animation settings
- version/status/approval

For the first vertical slice, use 2–3 user-supplied or clearly licensed assets. Do not build stock-provider search or generative-image integration until manual assets prove the edit.

MiniTimeline / TimelineItem:

- ordered typed items: source clip, narration/visual, optional transition
- explicit media/version references
- calculated start/duration
- audio settings
- subtitle reference
- dependency fingerprint

Rendering:

- FFmpeg adapter consumes validated timeline data.
- Generate captions from known script plus measured narration timing; retain editable caption cues.
- Mix source audio and narration with configurable targets. Treat any LUFS target as a tested preset, not a hard-coded universal truth.
- Render MP4 using versioned preset configuration.

Mini-video QC:

- all dependencies current and approved
- no missing/unplayable assets
- expected streams, resolution, frame rate, duration, codecs
- no unintended timeline gaps or overlaps
- caption timing/bounds checks
- silence and peak/loudness warnings with configurable thresholds
- render log and checksum retained

GATE F — GO/NO-GO PRODUCT GATE

A human must review the finished 60–120 second MP4 and record:

- editorial usefulness
- source/commentary clarity
- timing and pacing
- narration quality
- visual sufficiency
- caption readability
- rendering reliability and duration
- actual provider and compute cost
- manual correction time
- rights/consent status for every asset

Do not scale to full videos until the result is acceptable and the dominant technical/editorial bottlenecks are documented.


PHASE G — SCALE TO MULTIPLE REACTION BLOCKS

Only after Gate F:

- Add ordered multi-selection workflow.
- Generate versioned intro after selected reaction points are approved.
- Generate versioned outro after reaction blocks are approved.
- Support multiple SourceClip and ReactionBlock pairs.
- Build full Timeline versions from explicit approved inputs.
- Regenerate only affected downstream branches using ArtifactDependency.
- Add transitions and background music only when they improve a real reviewed edit.
- Add preview/proxy rendering before full-quality rendering if measured performance requires it.
- Load-test storage, queue concurrency, cancellation, retries, and duplicate-job prevention.

GATE G

A full project with multiple blocks, intro, outro, narration, visuals, captions, audio mix, timeline, render, and QC must be reproducible from recorded approved versions without hidden manual files.


PHASE H — OPTIONAL VOICE LAB

This phase is not required for a finished video.

- Create VoiceProfile and consent/authorization records.
- Encrypt/restrict raw reference recordings and log access.
- Support export and verified deletion.
- Separate training/reference assets from generated narration.
- Test revoked consent, deleted provider model, missing reference data, and provider failure.
- Never clone another person's voice without documented authorization.

GATE H

Do not enable cloning for ordinary use until consent, access control, provider-policy review, retention, deletion, abuse prevention, and audit tests pass.


PHASE I — OPTIONAL METADATA, THUMBNAIL, AND PUBLISHING

Keep publishing separate from rendering.

- Generate versioned title, description, chapters, tags, and thumbnail candidates.
- Require explicit human approval of the exact RenderedVideo, metadata version, thumbnail, visibility, and schedule.
- Use least-privilege credentials, secure token storage, idempotent upload requests, and resumable/retry-safe behavior.
- Verify current YouTube API/platform rules immediately before implementation.
- Default to preparing an upload package; automated publishing is an optional final capability.

GATE I

No upload or schedule action may occur from a generation request alone. Publishing requires an explicit, auditable user action and must never expose credentials or publish a stale/unapproved render.


TEST STRATEGY

Minimum coverage across applicable phases:

- Model constraints, ownership, ordering, versioning, protection/cascade decisions, and timestamps.
- Service transaction rollback and idempotency.
- Provider/client contract tests using fakes and malformed fixtures.
- Cross-user and staff authorization.
- POST/CSRF enforcement for mutations.
- Dependency invalidation and preservation of unaffected branches.
- Migration tests from the preceding state with forward/reverse behavior where safe.
- Media fixture tests for missing streams, bad duration, invalid MIME, corrupt files, cancellation, timeout, and subprocess failure.
- End-to-end vertical slice with fake providers and tiny generated media.
- Separate opt-in live smoke tests, never part of the normal deterministic suite and never run with production publishing credentials.


OBSERVABILITY, COST, AND SAFETY

Before enabling any external provider or worker:

- define timeout, retry count, maximum input/output size, and per-job/project cost limits
- use structured logs with correlation/job IDs and no secrets/raw tokens
- store sanitized provider error categories, not raw sensitive payloads
- expose job progress, cancellation status, and actionable failure messages
- meter provider usage and render duration
- prevent duplicate active jobs with idempotency constraints
- define storage quotas and retention
- validate all files and URLs; block private-network URL fetching unless explicitly required and secured
- document how operators stop workers, revoke credentials, restore backups, and reconcile orphaned files/jobs


REVISED MILESTONES

1. Approved transcript -> validated analysis run.
2. Analysis -> ordered selected segment.
3. Selected segment + authorized local media -> validated source clip.
4. Source clip -> evidence-backed approved ReactionBlock.
5. ReactionBlock -> approved standard-voice narration.
6. One source clip + reaction + 2–3 visuals + captions -> QC-reviewed 60–120 second MP4.
7. Multiple approved blocks -> reproducible full timeline and render.
8. Optional voice cloning after consent/security gate.
9. Optional metadata/thumbnail package.
10. Optional explicit publishing after credential/policy gate.
